# Kantar Data Science Take-Home — Fraud Detection

This repository contains a reproducible Python analysis of the supplied registration dataset. It addresses both assignment tasks:

1. **Anomaly detection:** identify the historical period with an unusually high concentration of labelled fraud, then demonstrate label-free anomaly-monitoring approaches.
2. **Fraud classification:** train and evaluate binary classifiers using `is_fraud` as the target.

The scripts are intentionally separated by task so that the analysis is easy to inspect and rerun. The analysis report is in `reports/analysis_report.md`.

## 1. Requirements

- Python 3.10 or newer (the supplied scripts were executed successfully with Python 3.13.5)
- pip
- The supplied Excel dataset in `data/dataset_20260430.csv.xlsx`

Create and activate a virtual environment from the project root.

### Windows PowerShell

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

## 2. Run the analysis

Run these commands from the top-level project directory, in this order:

```bash
python src/01_data_quality_eda.py
python src/02_anomaly_detection.py
python src/03_fraud_classification.py
python src/04_generate_report.py
```

The first script creates data-quality summaries, target distribution and fraud-rate summaries by category. The second creates daily/hourly time-series summaries, statistical volume flags and an Isolation Forest example. The third fits Logistic Regression and Random Forest pipelines and writes held-out test metrics. The fourth builds the Markdown report from the generated results.

## 4. Methodology notes

### Anomaly detection

The retrospective investigation uses `is_fraud` to quantify the fraud concentration after the fact. The candidate event is then compared with the hourly registration-volume baseline. For the label-free demonstration, Isolation Forest receives hourly registration volume and time-context features only; it is not trained on the fraud label. An anomaly flag means unusual activity, not confirmed fraud.

### Classification

The target is imbalanced (5% fraud in the supplied data). The evaluation therefore reports precision, recall, F1, ROC-AUC and average precision rather than relying on accuracy alone. A stratified 80/20 random split is used with `random_state=42`. All imputing, scaling and encoding are inside scikit-learn pipelines and are fitted only on the training split. `user_id` and the raw timestamp are excluded. Time-of-day and day-of-week features are engineered from the timestamp; registration duration is log-transformed.

Logistic Regression uses class weights and serves as an interpretable baseline. Random Forest uses balanced subsampling and provides a nonlinear comparison. The model selected in the report is the model with the higher average precision on the test split; this does not establish that it is the best model for every operational cost function.

## 5. Important limitations

- The dataset covers only 30 days. It cannot establish long-term seasonality or robust future-period generalization.
- A random stratified split can put records from the same time-localized fraud event in both training and test sets. The resulting metrics may be optimistic for a future deployment. A chronological holdout and data from later periods are important next steps.
- No IP address, session identifier, referral source or device fingerprint is supplied, so the analysis does not claim to identify a coordinated actor or attack infrastructure.
- Demographic and lifestyle variables can be sensitive or act as proxies. They should receive governance review before operational use; model associations are not causal explanations.
- The model output is a risk score for investigation, not an automatic finding of fraud. Threshold selection should reflect the cost of missed fraud, false positives and available review capacity.

## 6. Reproducibility

The random seed, split ratio, feature list, selected model and test metrics are recorded in `outputs/classification_metrics.json`. Dependencies are listed in `requirements.txt`. Re-running the scripts regenerates the analysis artefacts.
